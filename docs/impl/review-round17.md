# 第十七轮：设备身份公钥的登记与下发

> 日期：2026-11-20 ｜ 目标轮次 8/20

## 一、补的是信任链的最后一环

上一轮做了 Ed25519 握手验签，但验签用的公钥是**硬编码种子**。
真实部署里必须有地方回答：「这个设备的公钥是哪来的？」

本轮把它接上：

```
设备首次绑定时登记 identity_pubkey  →  PG devices.identity_pubkey
        ↓
建会话时两端都能读 /v1/connect/keys  →  拿到对方公钥
        ↓
握手时用这把公钥验签              →  中继冒充失败
```

## 二、服务端改动

| 层 | 改动 |
|---|---|
| 迁移 | `devices.identity_pubkey text NOT NULL DEFAULT ''` |
| store | `Device.IdentityPubKey` + `UpdateDeviceIdentity` / `GetDeviceIdentity`（内存 + PG 双实现） |
| gateway | `POST /v1/devices/identity`（需账号 token + 设备凭证）<br>`GET /v1/connect/keys?session_id=`（仅会话参与方） |

### 两条接口的边界

```
POST /v1/devices/identity
  - 必须带账号 token + X-Device-Token
  - 公钥必须是 32 字节 hex（64 字符）
  - 只能登记自己账号下的设备

GET /v1/connect/keys
  - 必须带账号 token
  - 调用方必须拥有该会话的 controller 或 target 设备
  - 返回双方公钥（不含任何私钥材料）
```

第二条的权限检查是重点：不检查的话，任何账号可以枚举任意会话的设备公钥，配合设备码就能拼出「谁的设备在跟谁连」。

## 三、验证（集成测试）

| 用例 | 断言 |
|---|---|
| 未认证登记 | 401 |
| 公钥长度非法 | 400/401 |
| **用别人的设备凭证登记** | **403** |
| 正常登记两端 | 200 |
| 会话参与方读公钥 | 200，且与登记值一致 |
| 被控端也能读 | 200 |
| **第三方账号读** | **403** |
| 两台设备公钥不同 | 长度 64 且互异 |

## 四、过程中遇到的问题

1. **401 vs 400 的错误码预期**：`AUTH_INVALID_CREDENTIAL` 映射到 401 而不是 400，测试按 400 写会红。已按实际映射修正断言。
2. **建会话需要验证码**：`/v1/connect/request` 要求被控端先轮换 captcha 再带上，测试一开始漏了这步。
3. **测试里用第二次 bind 的凭证去登记第一台设备** —— 403。设备凭证是绑定到具体设备的，不能混用；这个失败本身也验证了鉴权是有效的。
