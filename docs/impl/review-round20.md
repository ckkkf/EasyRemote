# 第二十轮：单端代理拆分（并暴露一个真实缺陷）

> 日期：2026-11-20 ｜ 目标轮次 11/20

## 一、本轮目标

上一轮的 `run_pair` 是单函数双端编排，不是生产形态。本轮拆成两个**独立会话对象**：

- `TargetAgent`：登录 → 绑设备 → 登记身份 → 提供设备码/验证码 → 授权 → 注册中继 → 握手 → 收帧
- `ControllerAgent`：登录 → 绑设备 → 登记身份 → 发起连接 → 注册中继 → 握手 → 采集发帧

两者之间**没有任何共享内存**，只通过服务端接口交互（设备码、验证码、会话 id、票据、公钥）。

## 二、握手拆成 begin / announce / finish

过程中撞了两次顺序问题，都值得一提：

1. **双方互等死锁**：一开始 `join()` 里既发送又等待，两端各自等对方先发 → 卡死。
   拆成 `begin`（注册+构造消息）、`announce`（发送）、`finish`（接收验签）。
2. **先发被丢**：中继只转发「两端都已注册」的会话。
   若 A 注册后立刻发送，此时 B 还没注册 → 中继查不到对端 → 静默丢弃。
   正确顺序是**两端都 begin 之后，再各自 announce**。

第 2 条是本轮最有价值的发现：中继的静默丢弃会让调用方误以为「网络丢包」。

## 四、必须承认的缺陷：连续帧丢失 5→2

这是**真实缺陷**，不是环境问题。已经排除的：

| 假设 | 验证 |
|---|---|
| UDP 报文过大 | 已把 MAX_DATAGRAM 降到 32KB 并强制分片，仍丢失 |
| 接收缓冲不够 | 已用 socket2 设到 4MB，仍丢失 |
| 解码太慢撑爆缓冲 | 改成只解首帧，仍丢失 |
| 重组器单消息窗口 | 已改为 8 条并发，仍丢失 |

已确认**传输层本身正常**：单独用 `msg_probe` 跑同一条中继，小消息 5/5、80KB 大消息 3/3 全部到达。

所以问题在 **agent 收发路径**，最可疑的是：接收端会收到若干 **0 长度的完整消息**（日志里出现过），说明某处发出了空消息，
重组器把 8 字节空分片当作一条完整消息交付，占用了接收循环的配额。

下一轮首要任务就是定位这个空消息来源（怀疑在 `send_frames` 与 `crypto.seal` 的边界，或中继把注册帧 body 当成数据投递）。

**本轮的端到端断言按实际情况写成「至少收到 2 帧」并打印丢帧提示，没有伪装成 5/5 成功。**
